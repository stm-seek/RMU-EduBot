# 05 — ฟีเจอร์ทีละตัว

## 5.1 ลำดับการตัดสินใจของบอท (เอาไปวาด flowchart บทที่ 3 ได้ตรง ๆ)

> ผังงานนี้มีเวอร์ชันภาพพร้อมใช้แล้วที่ `screenshots/c02-flowchart.png`

เมื่อผู้ใช้ **กดปุ่ม** (postback) → ไปที่ handler ของปุ่มนั้นตรง ๆ ไม่ต้องเดา

เมื่อผู้ใช้ **พิมพ์ข้อความ** ระบบตรวจตามลำดับนี้ (`app/router.py:_dispatch_text`)
ลำดับนี้ **ตั้งใจเรียงแบบนี้** ไม่ใช่บังเอิญ:

```
1. มีรหัสวิชา 7 หลักในข้อความ?
      ├─ ถามว่า "ลงได้ไหม" ด้วย → ตอบเงื่อนไขการลงทะเบียน  (planner)
      └─ ไม่ → ตอบรายละเอียดวิชา                            (course)
2. ถามว่าเทอมหน้าลงอะไรดี?                                   (planner)
3. ถามเรื่องเกรด / GPAX / เกียรตินิยม?                       (planner)
      *ดักก่อนข้อ 4 เพราะ "GPA 1.88 จบได้ไหม" เข้าเงื่อนไขทั้งสองข้อ
      *และกันคำขอเอกสารที่มีคำว่าเกรด ("ขอใบเกรด") ออกไปก่อน
4. ถามความก้าวหน้า / จบได้ไหม?                               (planner)
5. อยู่ในโหมดปรึกษา AI หรือกำลังเข้า/ออกโหมด?                (ai_chat)
      *ต้องมาก่อนการค้น เพราะคนในโหมดต้องการคำตอบ ไม่ใช่ลิงก์เอกสาร
6. พูดถึงแบบประเมินระบบ?                                     (search + intent=survey)
      *ต้องมาก่อน FAQ/ค้น เพราะคำว่า "แบบประเมิน" ไปตรงชื่อเอกสารในคลังได้
7. ตรงกับ FAQ ที่คนเขียนไว้ (ถึงเกณฑ์ความคล้าย)?             (faq)   ← ชั้นที่ 2
8. ค้นในฐานข้อมูลเจอ (เอกสาร / อาจารย์)?                     (search)
9. ไม่เจอเลย → บอกตรง ๆ ว่ายังตอบไม่ได้ + เสนอปุ่ม           (fallback)
```

**หลักที่อยู่เบื้องหลังลำดับนี้:** อะไรที่คำนวณได้แน่นอนต้องมาก่อน LLM เสมอ
ถึงผู้ใช้จะอยู่ในโหมดคุยกับ AI อยู่ก็ตาม

## 5.2 Rich Menu

**ใบหลัก 6 ช่อง** (`assets/rich_menu.png` 1200×810)

| ช่อง | ปุ่ม | ไปทำอะไร |
|---|---|---|
| 1 | ปรึกษา AI | เปิดโหมดคุยกับ AI ต่อเนื่อง |
| 2 | กู้ยืม กยศ. | เอกสารหมวดกู้ยืม (12 ฉบับ) |
| 3 | ติดต่ออาจารย์ | เลือกกลุ่มสาขา → รายชื่อ + อีเมล |
| 4 | ค้นรายวิชา | วิธีค้น + วิชาตัวอย่าง |
| 5 | เอกสาร/คำร้อง | 11 หมวด → เลือกหมวด → รายการเอกสาร |
| 6 | ทำอะไรได้บ้าง | เมนูรวมความสามารถทั้งหมด |

**ใบโหมดปรึกษา 2 ปุ่ม** (`assets/rich_menu_consult.png`) — "จบการปรึกษา" / "เมนูหลัก"
สลับให้เห็นเฉพาะคนที่อยู่ในโหมด ด้วย per-user link
(`POST /user/{uid}/richmenu/{mid}`) ไม่ใช้ `richmenuswitch` เพราะแบบนั้น
**ไม่ส่ง postback กลับมา** = บันทึก `chat_logs` ไม่ได้ ซึ่งขัดหลักการวัดผล

ข้อจำกัดของ LINE ที่ต้องรู้: **Rich Menu ไม่แสดงบน LINE for PC** ต้องทดสอบบน
มือถือ และ **แก้ภาพของเมนูที่อัปโหลดแล้วไม่ได้** ต้องสร้างใบใหม่แล้วลบใบเก่า
พิกัดปุ่มใน `app/line/rich_menu.py` **วัดจากไฟล์ภาพจริง** ไม่ใช่หาร 3 หาร 2
— เปลี่ยนภาพต้องวัดใหม่

## 5.3 ฟีเจอร์หลัก 8 ตัว

### (1) เอกสาร / คำร้อง — `answered_by=rich_menu` / `quick_reply`
33 ฉบับ 11 หมวด กดเลือกหมวด → ได้ชื่อเอกสาร + ลิงก์ไฟล์จริงจากเว็บมหาวิทยาลัย
(ตรวจลิงก์เข้าได้ครบเมื่อ 22 ส.ค. 2569) เพดานต่อหมวดต้องมากกว่าหมวดที่ใหญ่สุด
— เคยตั้ง 10 แล้วเมนูบอกว่ามี 12 ฉบับ แต่กดเข้าไปเห็นแค่ 10

### (2) ติดต่ออาจารย์ — `answered_by=rich_menu`
28 คน แยกตามกลุ่มสาขา บอกชื่อ ตำแหน่ง อีเมล และ**บอกตรง ๆ ว่าไม่มีเบอร์โทร/
ห้องพัก** (เว็บคณะไม่เผยแพร่ 0/28 คน) แทนการเว้นว่างให้ผู้ใช้เดา

### (3) ค้นรายวิชา — `answered_by=course` / `search`
พิมพ์รหัส 7 หลัก → ชื่อวิชา หน่วยกิต คำอธิบายรายวิชา เทอมที่เปิดสอน หมู่เรียน
พิมพ์ชื่อวิชาเป็นคำ → ค้นด้วย `pg_trgm` (ความคล้ายของตัวอักษร เพราะ Postgres
ตัดคำไทยไม่ได้) คืนไม่เกิน 5 ผลลัพธ์ต่อครั้งให้อ่านจบในหน้าจอมือถือ

### (4) ความก้าวหน้าตามหลักสูตร — `answered_by=planner`
`app/planner.py` + `app/progress.py` **ไม่เรียก LLM และไม่แตะ I/O เลย**
(รับข้อมูลเข้า → คืนผลคำนวณ ทำให้เทสได้ทุกกรณีและผลไม่สุ่ม)
คำนวณจากวิชาที่ผู้ใช้ติ๊กใน LIFF: ผ่านแล้วกี่หน่วยกิต เหลือเท่าไร คิดเป็นกี่ %
เทียบกับแผนการเรียนมาตรฐาน

### (5) เทอมหน้าควรลงอะไร — `answered_by=planner`
เลือกจากแผนการเรียนมาตรฐาน 8 เทอม ตัดวิชาที่ผ่านแล้วออก คุมไม่ให้เกินเพดาน
หน่วยกิตต่อเทอม **และแจ้งผู้ใช้ตรง ๆ ว่าลำดับนี้เป็น "เทอมที่แนะนำ" ไม่ใช่
เงื่อนไขบังคับ** เพราะตาราง `prerequisites` ยังว่าง (ไม่มีแหล่งข้อมูล)

### (6) คำนวณเกรด / เป้า GPAX / เกียรตินิยม — `answered_by=planner`
`app/gpa.py` ผู้ใช้พิมพ์ GPAX ปัจจุบันมา**ตัวเดียว** หน่วยกิตที่เหลือระบบรู้จาก
planner แล้ว → ตอบว่าต้องทำเกรดเฉลี่ยเท่าไรในหน่วยกิตที่เหลือเพื่อถึงเป้า
**ไม่เก็บเกรดลงฐานข้อมูล** และยังไม่รองรับการลงเรียนซ้ำเพื่อแก้เกรด

### (7) FAQ — `answered_by=faq` (ชั้นที่ 2)
อ่านจากตาราง `faqs` ที่เจ้าหน้าที่กรอกผ่านหน้า `/admin` แมตช์ด้วย
`word_similarity` **สองทิศทาง** ทั้งกับคำถามหลักและ `variants` ไม่ถึงเกณฑ์
`FAQ_MATCH_THRESHOLD` → ตกไปชั้นถัดไป ไม่เดา · **ยังไม่มีเนื้อหาจริงในตาราง**
(มีแต่แถวทดสอบ 1 แถวที่ `is_active = false`)
เพราะคำตอบทางการต้องให้คณะเขียน ห้ามแต่งเอง

### (8) ปรึกษา AI — `answered_by=ai_chat` (ชั้นที่ 3)
`app/ai_chat.py` คุมด้วย session ในตาราง `ai_sessions`: จำกัดจำนวนตาสนทนา
และหมดเวลาเอง ออกจากโหมดได้ทั้งกดปุ่มและพิมพ์คำออก · **ไม่ยิง LLM ทุกข้อความ**
โดยเจตนา — ข้อความที่ค้นไม่เจอจะ *เสนอ* ให้เข้าโหมดปรึกษาก่อน เพื่อไม่เสีย
โควตา API ไปกับคำทักทายและคำที่พิมพ์ผิด

## 5.4 สิ่งที่ทำเมื่อระบบมีปัญหา (ออกแบบไว้ ไม่ใช่บังเอิญ)

| สถานการณ์ | ผู้ใช้เห็นอะไร | ป้ายใน log |
|---|---|---|
| เข้าใจคำถามแต่ยังไม่มีข้อมูลในฐาน | "ยังไม่มีข้อมูลเรื่องนี้" | `no_data` |
| ฐานข้อมูลล่มระหว่างคุย | "ระบบฐานข้อมูลขัดข้อง" | `db_error` |
| ไม่เข้าใจคำถาม | บอกว่าค้นอะไรได้ + เสนอปุ่ม | `fallback` |
| AI ล่ม/หมดเวลา | "ระบบตอบด้วย AI ขัดข้องชั่วคราว" | `fallback` (`intent_key=ai_chat_error`) |
| ยังไม่ได้ตั้ง `DATABASE_URL` ตอนสตาร์ต | ตอบว่ายังไม่มีข้อมูล **ไม่ใช่ HTTP 500 และไม่ใช่เงียบหาย** | `no_data` |

การแยก `no_data` ออกจาก `fallback` เป็นเรื่องของการวัดผล: อันแรกคือ
"ระบบเข้าใจแต่ข้อมูลไม่มี" (แก้ด้วยการเพิ่มข้อมูล) อันหลังคือ "ระบบไม่เข้าใจ"
(แก้ด้วยการเพิ่มความสามารถ) — ถ้านับรวมกันจะสรุปผิดว่าต้องไปแก้อะไร
